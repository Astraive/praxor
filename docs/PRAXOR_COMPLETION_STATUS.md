## How much is done

**Praxor is not release-complete.** The tracker has closed 40 of 59 issues (67.8%) and merged 40 of 43 PRs. Nineteen issues and two draft PRs remain open. The epic has checked its first durability batch, while its other five high-level release phases remain unchecked. These are tracker counts, **not** a defensible percentage of a finished SQL/document/vector/relational engine: the remaining work includes core ownership, crash recovery, physical history proof, atomic catalog operations, language breadth, migration, and release validation. New feature and verification issues will be needed once the release profile is specified.

## Work still to specify for a full multi-model engine

The current issue set does **not** exhaust the requested SQL + document + vector + relational scope. Before calling Praxor complete, add tracked, testable issues for each missing release-profile capability. Use [architecture](architecture.md) as the ownership direction and [query readiness](query-readiness.md) as the present executed-versus-unsupported baseline. At minimum the profile needs:

1. **One semantic pipeline and catalog:** state precisely which SQL syntax, typed expressions, joins, grouping, ordering, limits, DDL, DML, constraints, and transaction isolation levels are supported. Parse, bind, plan and execute against the same durable catalog/record owner. Unsupported syntax must fail explicitly, never silently return a plausible no-op plan or success.
2. **Document and relational access:** define document schema/JSON semantics, mutations, indexing and query predicates alongside relational rows and constraints. Prove stable record identity and identical snapshot/transaction visibility across point reads, scans and index reads.
3. **Vector, graph and search indexes:** define exact-reference oracles, ANN recall and update/delete/reopen behavior, graph edge/traversal semantics, and any full-text/geo release claims. Verify index consistency through WAL recovery, compaction, snapshot pinning and schema changes. Do not infer production readiness from an index type's existence or a benchmark name.
4. **Cross-model transactions:** specify which operations share one commit sequence and recovery unit, how secondary indexes are maintained atomically, and how conflicts, failures and retries appear to callers. Prove current and historical read consistency at supported isolation levels.
5. **Compatibility and operations:** publish format migration/import rules, backup/restore and version-skew behavior, corruption/repair boundaries, replication guarantees if claimed, observability, resource limits and operator recovery procedures. Any unsupported legacy root or feature must fail before mutation.

For each feature, record an executable positive example, a negative/capability case, crash/reopen behavior, resource bound, and cross-platform verification. A release can deliberately exclude a capability only if the public contract says so and callers receive a typed refusal.

## Release gates before declaring Praxor complete

- Every required issue has an acceptance test, independent design/source review, exact-head Linux and Windows CI, and a normally merged PR. Keep failing RED PRs draft. The merged default must pass its own CI; test results from an ancestor or only one platform are insufficient.
- Run locked full/focused suites, strict formatting/Clippy, feature matrix, native storage-boundary scripts and benchmark smoke with the committed workflow and source manifest. Use isolated D:/F: worktrees/targets, `--locked --jobs 2`, and the existing local physical-RAM gate for Cargo. Preserve dirty original checkouts.
- Run model-based concurrency, deterministic fault injection at every acknowledged durability/publication boundary, process-exit and repeated-crash recovery, corrupt/forged metadata and WAL/value/segment tests, fuzz/property tests for parsers and codecs, long soak, and supported-format migration/backup/restore tests. Record Windows and Linux behavior separately; do not present process-exit evidence as a power-cut guarantee.
- Measure representative storage and query workloads with disclosed hardware, durability mode, data shape, cache size, concurrency, correctness level, tail latency, memory, recovery time, and read/write/space amplification. Compare against pinned baselines and enforce explicit regressions/budgets rather than a bare speed claim.
- Publish the final supported API/format/feature matrix, compatibility policy, release guarantees and deliberate limitations. Only after those gates pass should [#3](https://github.com/Astraive/praxor/issues/3) and the Praxor release milestone close.
